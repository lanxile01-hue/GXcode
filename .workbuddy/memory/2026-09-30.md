## 上下文窗口机制排查（只读分析，未改动代码）

应「当前可用上下文窗口多大 / 上限如何确定 / 用量比例 / 超限如何处理」的提问，通读了
`config.py`、`context/manager.py`、`context/token_counter.py`、`context/summarizer.py`、
`context/file_spill.py`、`main.py`，梳理出已实现的机制与两处设计缺口。

### 已实现的机制（全部走默认值）

- `gxcode.yaml` 无 `context:` 节 → `ContextConfig` 全部默认：`window_size=200_000`、
  `auto_margin=13_000`、`manual_margin=3_000` → 自动压缩阈值 **187,000**，`/compact` 手动阈值 **197,000**。
- 层1 溢写：单条 tool_result > 8,000 字符 或 合计 > 16,000 字符 → 存盘 `.gxcode/spills/`，留 500 字符预览。
- 层2 兜底：`Summarizer.compress()` 尾部保留 `keep_tokens=10_000` / `keep_min=5` 条，
  只摘要 assistant + tool_result，**user 消息原文保留**，压缩后追加 `BOUNDARY_MESSAGE` 提醒不要脑补。
- 熔断：`max_summary_failures=3`，连续失败后 `tripped=True`，不再尝试摘要。
- 估算：`TokenCounter`，`chars_per_token=4.0`，API usage 锚定 + 增量字符估算。
- 会话恢复：`memory/session_recovery.py` 的 `max_chars=600_000`（≈150K tokens）。

### 发现的两个缺口（待确认是否要修）

1. **`window_size=200_000` 是硬编码默认值，从不与 provider 实际模型校验。**
   当前 `gxcode.yaml` 的 `active: deepseek` → `model: deepseek-chat`。若该模型真实窗口 < 200K，
   压缩触发点会偏晚，可能直接被 API 报错截断。建议 provider 配置增加 `window_size` 字段并透传到 `ContextConfig`。
2. **压缩后 `TokenCounter` 锚点失效 -> 退化为纯字符估算，此时漏算 system prompt 与工具 schema 的开销。**
   锚定期间（首次 API 调用后）`_anchor_total` 含真实 prompt_tokens，开销被覆盖；一旦压缩使
   `_content_match` 失败，全量估算只累加 `m.content`，system prompt / tools_schema 不计入 → 系统性低估。

### 其他

- 本机 `~/.workbuddy/models.json` 为空数组，`settings.json` 无 model/token 字段，
  即该会话层的窗口大小在本地不可读。

## 「讲到迭代 4 就停」根因定位（只读分析，未改动代码）

现场：会话 `.gxcode/sessions/20260930-111303-13c4.jsonl`（11:24:52 起，用户问「我的整个项目的大概内容」），
日志停在 11:25:00 一句纯文本「让我再看看主要目录的代码结构。」，无 tool_result 跟进。

迭代回放：i1 `run_command(ls)`（Windows cmd 无 ls，失败）→ i2 `glob`（拿到文件树）→ i3 `read_file`×3
（GXCODE.md / pyproject.toml / gxcode.yaml）→ i4 模型只输出一句「让我再看看…」，**没有发出 tool_calls**。

根因（设计行为，非崩溃）：`agent/loop.py:132` 的停止条件是「本轮无工具调用 → reason="finished" 直接 return」。
所以模型把「打算继续」的旁白当成收尾语输出时，循环立刻判定任务完成退出 —— 属于 ReAct 循环的正常终止路径。

放大问题的三个因素：
1. `prompts.py` / `prompt_builder.py` 全 7 个模块都没有约束「要调用工具就必须在同一轮调用，不要只说不做」，
   模型不知道纯文本 = 结束。
2. 历史保真度差：`loop.py:163` 只存 `turn.text`，assistant 的 tool_calls 从不入 history；
   `session.py:64` 把工具结果拼成 `role="user"` 的 `[tool_result from X]`。模型看不到自己调用过工具，容易漂到"解说模式"。
3. `tui/app.py:300-310` 只在 cancelled / max_iterations / tool_error_loop / stream_error / 空 finished 时打印提示，
   **正常的 finished 静默无输出** → 用户看到「迭代 4」标记后什么都没了，因此困惑。

顺带发现（独立 bug）：`tools/system_tools.py:43,45` 用 `stdout.decode("utf-8")` 解 Windows cmd 的 GBK 输出，
导致 stderr 中文乱码（日志里 `'ls' ������...`）。应改用 `locale.getpreferredencoding()` 或 `mbcs`/`cp936`。

### 问题 A：上一轮修复根本没生效（非代码问题）

### 问题 B：溢写自我递归（真 bug，已修）
