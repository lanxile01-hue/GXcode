# 2026-09-27

## 梳理 GXCode 基础工具系统的实现位置

用户询问项目中「文件修改、命令执行」等基础工具的落点，通读后确认完整六层链路：

1. 定义层 `src/gxcode/tools/base.py` — `Tool` 抽象基类（`name/description/parameters/is_safe`）+ `ToolResult.ok/fail`
2. 实现层 `src/gxcode/tools/file_tools.py`（read_file / write_file / edit_file）、`src/gxcode/tools/system_tools.py`（run_command / glob_find / grep_search）
3. 注册层 `src/gxcode/tools/registry.py`（`ToolRegistry.to_api_schema()`）、`tools/__init__.py:create_default_registry()`
4. 装配层 `src/gxcode/main.py` — `to_api_schema()` → `create_provider(tools=...)`，并 `build_act_prompt(registry.list_all())` 写入 System Prompt
5. 调度层 `src/gxcode/agent/loop.py` — 按 `is_safe` 分离后并发 safe / 串行 unsafe，`_execute_tool()` 内跑权限检查
6. 权限闸门 `src/gxcode/permission/checker.py` — 黑名单 → 沙箱 → 权限模式 → 规则引擎 → 人在回路

## 梳理 MCP 协议适配 + 模型接口统一 + ReAct 循环

- MCP 链路（6 个脚本）：`mcp/config.py`（两层 YAML 合并 + `${VAR}` 展开）→ `mcp/manager.py`（`connect_all()` 逐个连接、单点失败只告警）→ `mcp/client.py`（JSON-RPC 2.0：`initialize` 协议版本 2024-11-05 → `tools/list` → `tools/call`）→ `mcp/transport.py`（`StdioTransport` / `HttpTransport`）→ `mcp/adapter.py`（`MCPToolWrapper` 把远端 `tool_def` 包成 `Tool` 子类）→ 与内置工具合流进同一个 `ToolRegistry`。
- 模型接口统一：`provider/__init__.py` 的 `Provider` ABC + `create_provider()` 工厂按 `protocol` 分发；`provider/openai.py`、`provider/anthropic.py` 各自解析流式事件，统一产出 `TextDelta / ThinkingDelta / ToolCall / UsageEvent`。
- ReAct 循环：`main.py:70` 注入 tools schema → `agent/collector.py` 双路收集（实时推 UI + 攒 `TurnResult`）→ `agent/loop.py` 按 `is_safe` 拆并发/串行并执行 → `session.py:add_tool_result()` 回灌 → 下一轮；五种停止条件在 `loop.py`。
- Plan Mode 收窄：`tui/app.py:228-238` `_get_active_registry()` 只返 read_file / glob_find / grep_search。

## 新发现的问题

- **Anthropic 工具 schema 格式不匹配（严重）**：`registry.to_api_schema()` 只产出 OpenAI 格式 `{type:function, function:{name,description,parameters}}`，而 `provider/anthropic.py:51-52` 直接 `body["tools"] = self._tools`。Anthropic Messages API 要求 `{name, description, input_schema}`。选 anthropic 协议时带工具的请求会被 400。所谓"统一适配"实为"只按 OpenAI 格式"。
- **工具结果回灌不是协议原生（严重）**：`session.py:59-69` 的 `add_assistant_message` 丢掉 `tool_calls`，`add_tool_result` 用 `role="user"` + `"[tool_result from X]"` 纯文本前缀。OpenAI 需要 assistant 带 `tool_calls` + `role:"tool"` 消息，Anthropic 需要 `tool_use` / `tool_result` content block。`ToolCall.tool_id` 解析出来却从未进历史。
- **Plan Mode 未真正收窄 schema（中）**：`main.py:70` 把全量 schema 烘焙进 Provider 实例，Plan Mode 下模型在 API 层仍看得到写工具，只能靠 `KeyError → 工具未注册` 兜底。
- `mcp/transport.py` `HttpTransport.__init__` 设 `self._session = None` 而 `connect()` 设 `self._client`，未 connect 就调用会 AttributeError。
- `agent/loop.py:146` 的"连续工具错误"只统计未注册工具，权限拒绝与执行异常不计入，停止条件覆盖窄于设计意图。

## 澄清「组装历史」的真实含义 + 实测出的一处 Bug

一次 LLM 请求体（`provider/openai.py:33-45`）是**两条独立通道**：
- `messages` 数组：`system`（提示词）+ `user`（任务）+ `assistant`（只有文本）+ `user`（`[tool_result from X]`）。`session.py` 组装的只有这一条。
- `tools` 顶层字段：由 `registry.to_api_schema()` 生成，`main.py:70` 启动时烘焙进 Provider 实例，全程不变。**工具不走 messages**，但会以纯文本形式在系统提示词的 `## 可用工具` 段里再出现一次（双重表达）。

**实测确认的 Bug（系统提示词写一次锁死）**：`session.py:48-53` 的 `add_system_message()` 带 `not any(m.role == "system" ...)` 守卫，一旦历史里有 system 消息就永不更新。而 `tui/app.py:139-140` 每轮请求前会按模式重建提示词并赋值 `self._session._system_prompt`（还直接捅了私有属性）。实测结果：把 `_system_prompt` 从「Plan模式提示词」改为「Act模式提示词」后再调 `add_system_message()`，history 里仍是 Plan 版。
后果：会话中途 `/plan` → `/do` 切换时，系统提示词不跟着变，但执行用的 registry 变了，导致两个方向都错——切到 act 后模型仍以为只能读（实际能写），切到 plan 后模型以为能写（实际撞 KeyError）。
修复方向：`add_system_message()` 改为「存在则原地更新首条 system 消息」，或在 `_handle_input` 里显式 replace。

`types_.py:7-11` 的 `Message` 只有 `role` / `content` 两个字段，是工具调用无法结构化回灌的**结构性根因**。

## 多层安全检查防线逐层核对（含一次自我更正）

`permission/checker.py:check()` 串起五层，但**只有层 1、2 真正在拦**：
- 层1 `blacklist.py` — 11 条不可配置正则，仅作用于 `run_command` 的 `command`
- 层2 `sandbox.py` — `resolve()` 后 `relative_to()` 判断越权 ✅ 实现正确
- 层3 `modes.py` — 四种模式枚举
- 层4 `rules.py` — 全局/项目/会话三层 YAML + fnmatch
- 层5 `checker.py:75-80` — 返回 `requires_confirm`，无消费方

**更正先前判断**：`tools/file_tools.py:_resolve_safe()` 的 `startswith` 前缀缺陷，在默认链路上**不可利用**。因为 `loop.py:217-218` 先跑权限检查，层2 的 `check_path()` 用了正确的 `relative_to()`，会先拦住。实测：`check_path("../MewagentX", cwd)` → 拦截；`_resolve_safe("../MewagentX")` → 放行。所以该缺陷应定性为「纵深防御失效」而非「可绕过漏洞」——只有当 `AgentLoop` 不传 `permission_checker` 时才会真正暴露。

**实测出的黑名单绕过与误杀**：`rm -fr /` 与 `rm -r -f /` 均**放行**（正则只写了 `-rf`）；但 `rm -rf /tmp/foo` 被**误杀**（`\brm\s+-rf\s+/` 会匹配任意 `/` 开头路径）。

**新发现问题**：
- **`/permission` 命令完全无效，且会破坏 Plan/Act 模式**：`commands/builtin/commands.py:170` 的 `ctrl.set_mode(mode)` 写的是 `GXCodeApp._mode`，与 `/plan`、`/do` 共用同一变量（`tui/app.py:249`）；而 `PermissionChecker.mode` 在 `main.py:118` 构造时定死、永不更新。后果：切 strict/permissive 对拦截行为零影响，且执行后 `_mode` 变成 `"strict"`，冲掉 Plan/Act 状态并让 `app.py:230` 的 `if self._mode == "plan"` 判断失效。
- **CUSTOM 模式是 fail-open**：`checker.py:76` 的 `if self.mode in (DEFAULT, STRICT)` 不含 CUSTOM，规则未命中就落到 `return allowed=True, reason="放行"`。名为「完全按自定义规则」却默认放行。
- `rules.py:79` 的 `add_session_rule()` 从未被调用 → 三层规则里会话层恒为空。
- `rules.py:60` 的 docstring 示例 `'Bash(git *): allow'` 用的是 Claude Code 的工具名，GXCode 实际是 `run_command`，照抄示例永远匹配不上。
- `rules.py:90` 用 `" ".join(str(v) for v in params.values())` 拼所有参数；`edit_file` 有 path/old_string/new_string 三个参数，拼成一串后按路径做 glob 基本失效。
- **沙箱只覆盖 3 个文件工具**：`install_skill` 会 `mkdir` + `write_text` 写盘（`skills/install.py:74-78`），但不在 `("read_file","write_file","edit_file")` 名单里 → 绕开层2；同时非 `run_command` 工具在 DEFAULT 模式下最终落到层5 的 `allowed=True`。即 **MCP 工具与 install_skill 实际是无条件放行**。
- `modes.py:9` 注释「permissive 除黑名单外全部放行」与实现不符：层2 沙箱在层3 模式判断之前，PERMISSIVE 下沙箱仍生效（行为更安全，文档不准）。
- `checker.py:10` 导入 `Rule` 但从未使用。

## 五层防御的实测决策矩阵（补充）

`checker.py` 的五层是**串联早退链**而非并联过滤器，层3 的两个分支都是提前 `return`，会短路层4 与层5。实测矩阵：

| 场景 | 层1 | 层2 | 层3 | 层4 | 层5 |
|---|---|---|---|---|---|
| STRICT · 只读 | 求值 | 求值 | 穿过 | 求值 | 求值 |
| STRICT · 写 | 求值 | 求值 | **返回** | 跳过 | 跳过 |
| DEFAULT | 求值 | 求值 | 穿过 | 求值 | 求值 |
| PERMISSIVE | 求值 | 求值 | **返回** | 跳过 | 跳过 |
| CUSTOM | 求值 | 求值 | 穿过 | 求值 | **不可达** |

结论：**层4 规则引擎只在 DEFAULT 与 CUSTOM 生效**。实测：加同一条 `Rule(tool="write_file", param="*", allow=False)` 后，DEFAULT/CUSTOM 拦截成功，STRICT/PERMISSIVE 仍放行（reason 分别是"strict 模式需确认"/"permissive 模式"）。

沙箱实测：传 `../MewagentX/hack.txt` 时**四种模式全部拦截** —— 层2 是整条链唯一无条件生效的层。

层4 参数拼接缺陷实测：规则 `deny write_file(*.env)` 拦不住 `.env`，因为 `param_str = ".env SECRET"`，`fnmatch` 失败。该层参数匹配实际只对单参数工具（`run_command`、`read_file`）可用。

规则语法静默失效实测：`_parse_rule('Bash(git *): allow')` → `Rule(tool='Bash', ...)`，解析成功但永不匹配实际工具名 `run_command`，不报错不告警。

**最小可用结论**：默认配置（DEFAULT + 无 rules.yaml）下，能产生 `allowed=False` 的路径只有两条——黑名单命中、规则显式 deny。其余全靠层5 的标志位，而标志位无人消费。

## 值得肯定的实现

JSON-RPC 请求 id 递增；`initialize` 后补发 `notifications/initialized`；`transport.py:49` 用 `proc = self._proc` 捕获本地引用避免异步竞态；两个 Provider 都做了 `json.loads("null")` 返回 None 的守卫；单个 MCP Server 连接失败不阻断整体启动。

## 发现的两个待修问题（可作面试加分点）

- `tools/file_tools.py:_resolve_safe()` 用 `str(resolved).startswith(str(cwd))` 判断越权，存在前缀绕过：cwd=/a/b 时 `/a/bc` 也会通过。应改用 `Path.is_relative_to()` 或逐段比较。
- `permission/checker.py` 的 `requires_confirm` 字段被生产但从未被消费（`agent/loop.py:_execute_tool` 只看 `allowed`，TUI 也未接），导致「层 5 人在回路」实际失效、STRICT 模式等同放行。
