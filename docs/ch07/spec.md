# GXCode Ch07 Spec — 双层上下文压缩

## 背景

当前 Agent 长时间运行会累积大量工具结果，导致 token 用量逼近模型窗口上限。需要一套压缩机制在有限的 token 预算内维持可用性。

## 目标

- 两层压缩：轻量预防（工具结果存盘）+ 重量兜底（LLM 摘要早期对话）
- 用户消息原文保留，不被摘要改写
- 不引入精确 tokenizer，用近似估算
- 压缩后不丢信息（可重新读取存盘文件）

## 功能需求

- **F1: 轻量预防** — 每次 API 请求前检查工具结果大小。单条超阈值存盘对话留预览+路径；单条消息工具结果合计超阈值挑大的依次存盘。
- **F2: 重量兜底** — 累积历史逼近窗口上限时调 LLM 生成结构化摘要。从尾部按 token 往回数保留 ~10K token 或至少 5 条近期消息，较早消息被摘要替换。
- **F3: 近似 Token 估算** — 锚定上次 API 返回的准确 usage，增量按字符数/4 估算。锚点失效时全量估算。
- **F4: 结构化摘要 Prompt** — 禁止模型调工具，要求先写分析草稿再写正式摘要，草稿用完丢弃。摘要按固定部分组织：任务目标/已完成操作/关键发现/当前状态/待办事项。
- **F5: 边界消息** — 压缩后插入提示消息，告知模型需要文件细节请重新读取，不要照着摘要脑补代码。
- **F6: 手动触发** — 用户可手动触发压缩，此时安全余量收窄到 3K（自动触发留 13K）。
- **F7: 熔断机制** — 摘要连续失败 3 次后停止后续压缩尝试，避免死循环。

## 非功能需求

- **N1:** 不引入精确 tokenizer 依赖
- **N2:** 轻量预防 < 10ms（文件 I/O 除外）
- **N3:** 摘要 LLM 调用复用现有 Provider，不带 tools
- **N4:** 压缩不改变 ChatSession 的外部接口
- **N5:** 无新外部依赖

## 不做的事

- 精确 tokenizer（tiktoken 等）
- 摘要策略机器学习优化
- 分级压缩（多级粒度）
- 压缩历史回滚/撤销

## 验收标准

- **AC1:** 工具结果 > 8K 字符被溢写到磁盘，对话只留预览+路径
- **AC2:** 多条工具结果合计 > 16K 字符时，最大的被依次存盘直到不超阈值
- **AC3:** 累积历史超过窗口-13K 时自动触发摘要
- **AC4:** 手动触发压缩时余量收窄到 3K
- **AC5:** 用户原始消息在摘要过程中不被改写
- **AC6:** 摘要后插入边界消息提示重新读取文件
- **AC7:** 连续 3 次摘要失败后熔断
- **AC8:** Token 估算与实际用量偏差 < 30%
