# GXCode 终端 AI 编程助手：面试问题与参考答案

> 说明：以下答案以当前仓库实现为基础；标注“生产化建议”的内容，是在现有机制之上应继续补强的设计，不代表当前代码已经完整实现。

## 二、GXCode 终端 AI 编程助手

### Agent 执行链路

#### 38. 请解释 GXCode 的 ReAct 循环：Thought、Action、Observation 分别对应什么？

GXCode 的 ReAct 循环是“模型决策 → 工具执行 → 结果回灌 → 再次决策”。Thought 是模型基于系统提示、用户任务和历史上下文进行的内部推理；Action 是模型输出的结构化 Tool Call，包括工具名和 JSON 参数；Observation 是工具执行后的结构化结果，包括成功输出或错误信息。AgentLoop 不依赖模型把 Thought 原样输出，而是依据是否产生 Tool Call 来推进循环；没有 Tool Call 时，就把文本当作最终答案。

#### 39. 模型如何知道当前有哪些工具、工具参数是什么以及工具何时应该调用？

启动时，本地工具和 MCP Server 工具统一注册到 ToolRegistry。Registry 将每个工具的名称、描述和 JSON Schema 参数传给 Provider，再由 Provider 放入 OpenAI 或 Anthropic 的请求。模型据此判断工具用途、必填参数和参数类型，并自主决定是否调用。系统提示还会说明工具使用规则，例如修改文件前先读取、危险操作需要谨慎；但真正的权限判断仍由 GXCode 在执行前完成，不能只信模型。

#### 40. 为什么使用 MCP 统一适配工具和模型接口？它相比自定义函数协议有什么优势？

MCP 把工具发现、工具描述和工具调用抽成标准协议。GXCode 通过 MCPToolWrapper 把远程 `tools/list`、`tools/call` 映射为内部统一的 `Tool` 接口，因此 AgentLoop 不需要知道工具来自本地、stdio 进程还是 HTTP Server；Provider 也只需要处理统一的模型工具 Schema。

相比每个工具各写一套自定义函数协议，MCP 的优势是生态互操作、工具可独立部署、传输层可替换、能力可动态发现，且能降低 Agent 编排层与具体工具实现的耦合。代价是需要处理协议版本、连接生命周期、鉴权、超时、重连和远程不可信内容；MCP 不是权限系统，仍必须在客户端和工具服务端做安全控制。

#### 41. 文件修改工具如何设计，才能避免模型直接覆盖用户文件造成不可逆损失？

当前工具已经要求修改前先 `read_file`，`edit_file` 采用唯一 `old_string` 替换，匹配 0 次或多次都会拒绝，从而减少误改。写操作还应经过路径沙箱和权限确认。

生产化设计应采用“最小补丁 + 版本校验 + 可恢复写入”：先读取并记录文件哈希或版本号，提交 unified diff/编辑操作，写入临时文件并原子替换；写前保留备份或 undo journal，写后重新读取并展示 diff，必要时让用户确认。若文件在读取后被外部修改，应因版本不匹配而拒绝覆盖，而不是静默覆盖。

#### 42. 命令执行结果如何回传给模型？标准输出、错误输出、退出码和超时信息是否区分？

`run_command` 使用子进程分别捕获 stdout 和 stderr，并把退出码追加到结果中；stderr 以 `[stderr]` 标记，退出码以 `[exit_code: N]` 标记。工具层用 `ToolResult(success, output, error)` 区分成功输出和失败原因。默认 30 秒超时，超时会终止进程并返回失败结果。生产化时应进一步使用结构化字段 `stdout/stderr/exit_code/timed_out/duration`，并处理进程组、子进程残留和输出上限。

#### 43. 连续 50 次工具调用任务全部完成，如何定义“完成”？

不能把“调用了 50 次”本身定义为完成。一次任务完成至少应满足：模型停止产生 Tool Call；所有必需工具调用返回成功；任务的可验证目标满足，例如文件内容、构建结果或测试结果符合预期；最终答复向用户说明结果和验证证据。当前 benchmark 的“完成”定义较窄：FakeProvider 第一轮调用工具、第二轮返回文本，且 LoopFinished 原因是 `finished`。它证明编排链路能跑通，不等同于真实代码任务成功率。

#### 44. 如何检测 Agent 陷入重复调用、无效调用或无限循环？

基础防线是 `max_iterations`（当前默认 25）、用户取消、连续未知工具错误达到 3 轮和流错误终止。生产化还应记录规范化的 `(tool_name, arguments)` 指纹，检测相同调用及相同失败结果的重复；记录状态变化、总耗时、Token、单工具次数和副作用次数。若连续若干轮没有新观察或目标进度，暂停并请求用户介入，而不是继续重试。

#### 45. 如果模型在修改代码后没有运行测试，你会如何设计执行策略？

在 system prompt 和代码任务策略中把“修改后验证”设为硬性流程：读取项目测试入口和配置，完成修改后自动选择最小相关测试，再根据结果决定是否扩大到完整测试。将验证作为任务完成条件；如果模型直接结束而检测到工作区有修改且没有测试证据，系统可追加一次“请运行相关测试并报告结果”的提醒，或在高风险模式下暂停等待确认。测试命令本身仍需经过权限、超时和输出限制。

### 安全控制

#### 46. 危险命令拦截是基于黑名单还是白名单？两者各有什么缺陷？

当前是黑名单优先：对 `run_command` 使用不可配置的高危正则，命中即拒绝；随后再经过沙箱、规则、权限模式和人工确认。黑名单易逐步兼容正常开发命令，但无法穷举别名、编码、解释器和组合攻击，存在漏放。白名单只允许明确的命令或参数，安全边界清晰，却容易误伤正常工作流，且规则维护成本高。实践上采用分层策略：高危黑名单硬拦截，有限白名单/能力策略控制可执行范围，再配合沙箱、资源限制和人工确认。

#### 47. 如何防止通过参数、管道、重定向、脚本文件或编码绕过危险命令检测？

不能只对原始字符串做几条正则。应先解析 shell 语法或改为不经 shell 的 argv 执行，递归检查管道、重定向、命令替换、子 shell、后台任务和脚本入口；对路径和参数规范化，展开常见编码/转义后再检查；脚本执行要读取或在受限环境中审查脚本内容，不能因为命令名是 `python`、`bash` 就放行。最终的可靠边界应是 OS 沙箱、最小权限、网络/文件系统隔离和资源配额；黑名单只能作为快速拒绝层。

#### 48. 项目目录限制如何处理符号链接、相对路径、路径穿越和大小写差异？

当前 `check_path` 对项目根和目标调用 `Path.resolve()`，再用 `target.relative_to(root)` 判断，能防止常见的 `../` 和符号链接逃逸。生产化还要校验不存在路径的父目录、创建/重命名时的最终落点，拒绝跨设备或特殊文件；Windows 上使用规范化绝对路径和大小写不敏感比较，避免大小写差异绕过；对 TOCTOU（检查后文件被替换）使用安全的目录句柄、`openat`/等价机制或沙箱执行。搜索类工具也必须复用同一条路径校验，不能只保护写文件。

#### 49. 权限规则和人工确认的优先级是什么？哪些操作可以自动执行，哪些必须确认？

安全优先级应是：硬性拒绝（危险命令/越权路径）高于一切；显式 deny 高于 allow；显式 allow 可免确认；未命中规则进入当前权限模式决定是否确认。GXCode 的设计是黑名单 → 沙箱 → 权限模式 → 规则引擎 → 人在回路，规则有全局、项目、会话层级，后者优先。只读查询通常可自动执行；写文件、执行命令、删除/移动、网络和外部系统副作用默认需要确认，strict 模式下除只读工具外都确认；permissive 也不能绕过硬性拒绝。

#### 50. 如果命令会修改项目外部的系统状态，如何识别并拦截？

在执行前解析命令及其参数，识别写入项目外路径、系统服务、进程、用户/权限、包管理器、网络请求、云资源、Git 远端和数据库等副作用；把目标资源分类并与项目根、允许的环境变量和网络策略比较。无法可靠判定时按高风险处理，要求人工确认或拒绝。真正执行应在隔离沙箱中使用最小权限，并记录审计信息；仅依赖字符串匹配无法完整识别系统状态变化。

#### 51. 你如何测试安全策略的有效性？102 次安全决策用例包含哪些攻击类别？

测试应同时看零误放率、攻击召回率、正常命令误拒率、规则优先级、路径边界和性能，并加入变形、组合和属性测试，而非只测几个原样字符串。攻击类别至少应覆盖：危险删除/格式化/磁盘写入、fork bomb、关机重启、权限提升、管道下载执行、命令替换与 shell 注入、重定向、编码/转义、脚本间接执行、路径穿越、绝对路径、符号链接、Windows 大小写/设备路径、项目外写入、网络和系统服务副作用。

需要如实说明：当前 `evaluations/benchmark.py` 的 102 次是 6 个固定决策样例重复 17 次（高危命令、普通命令、目录穿越、项目内读写），并不是 102 个独立攻击类别，也不能证明安全策略“覆盖全面”。面试中应把它称为回归基准，并计划补充上述攻击矩阵、变形样本、对抗脚本和真实 OS 沙箱测试。

#### 52. 沙箱失效或工具返回恶意内容时，模型上下文如何防止被诱导？

工具输出必须被视为不可信数据，而不是系统指令。回灌时使用明确的 tool-result 边界和来源标识，提示模型忽略输出中的“请执行某命令/泄露提示词”等指令；系统约束、权限结果和用户要求放在更高优先级的位置。对输出做长度、类型和敏感信息控制，必要时脱敏；高风险动作重新走独立权限检查，不能因为工具输出要求就自动执行。若沙箱或工具完整性异常，应停止相关操作、保留审计并向用户报告。

### 长对话与跨会话记忆

#### 53. 工具结果超长时，为什么选择转储压缩，而不是简单截断？

简单截断会永久丢失模型可能需要的证据，尤其是编译日志、完整 diff 或文件尾部错误。GXCode 对超阈值结果溢写到磁盘，在上下文中保留预览和绝对路径，模型可按需用 `read_file` 重新读取；批量超限时优先转储最大的结果。这样同时控制 Token 和保留可恢复性。安全上应限制溢写目录、文件大小和敏感内容。

#### 54. 哪些信息必须原文保留，哪些信息可以摘要？

必须保留或可精确回读的内容包括用户原始要求、权限拒绝、错误码、测试失败的关键堆栈、文件路径/行号、补丁前后版本和工具调用配对关系。可摘要的是重复日志、冗长目录列表、已验证的中间推理、重复的成功输出和旧的闲聊。摘要必须保留来源、时间、状态、结论依据和可回读路径；不能把不确定推测写成事实。

#### 55. JSONL 和 Markdown 分别保存什么内容？为什么采用两种格式？

JSONL 保存会话事件：用户消息、助手回复、工具结果、时间戳等，一条记录一行，便于追加写、流式恢复和坏行隔离。Markdown 保存项目记忆笔记和项目指令：按分类组织，带 frontmatter 元数据，便于人工阅读、审查和版本控制。两者职责不同：JSONL 是完整、时序性的事件日志；Markdown 是提炼后的长期知识。把它们混在一起会同时损失机器恢复能力和人工可维护性。

#### 56. LLM 提炼项目记忆时，如何避免把错误结论永久写入记忆？

记忆写入应是低信任、可审计的提议流程：只从用户明确陈述、已验证工具结果和成功测试中提取；要求 LLM 输出来源、置信度、时间和分类；新笔记先进入 pending/quarantine，或在高风险类别要求用户确认。写入前做事实校验、去重和冲突检测，保留原始会话引用；支持版本、撤销和过期，而不是不可逆覆盖。当前项目已有四类 Markdown 笔记和 LLM 去重，但生产化还应补确认、来源和回滚。

#### 57. 跨会话注入项目记忆时，如何处理过期信息和冲突信息？

每条记忆应带更新时间、来源、作用域、版本和置信度；注入前按项目级优先于用户级、更新且已验证优先于旧信息，并只注入与当前任务相关的索引。发现冲突时不要静默合并，应明确标注冲突并请求用户确认；已过期信息降权、隔离或淘汰。记忆内容仍是不可信上下文，不能覆盖当前用户指令或权限规则。

#### 58. 如何保证会话持久化在进程异常退出时不丢数据？

当前采用 JSONL 追加写：每条消息独立一行，因此异常通常最多损失正在写入的最后一行；恢复时跳过坏行，处理孤儿工具调用，并检查上下文超限。更强保证需要每条记录写入临时缓冲后 `flush`/`fsync`，必要时按批次加校验和或 sequence number，并用锁避免多进程交错写。恢复后应校验最后一行、补写关闭标记或标记 session 为 incomplete，而不是假设会话正常结束。

#### 59. SSE 在这个项目中承担什么作用？断线重连、重复消息和消息顺序如何处理？

SSE 用于承载模型和 UI 的流式事件：文本增量、思考增量、工具调用参数片段、用量和结束事件，用户不必等待整段回复。事件解析应按 provider 适配，并通过 request/turn ID、事件序号和工具调用 ID 去重、重组和校验顺序。断线时可在仍具幂等性的请求上有限重连，使用 `Last-Event-ID` 或应用层 cursor；非幂等工具调用不能盲目重放，应先查询执行状态或让用户确认。当前 Provider 已解析 SSE，但完整的断线重连协议需要继续补强。

#### 60. asyncio 并发执行时，哪些任务可以并发，哪些必须串行？

互不依赖的只读工具可以并发，例如多个 `read_file`、`glob_find` 或 `grep_search`；当前 AgentLoop 按 `is_safe=True` 使用 `asyncio.gather()`。写文件、命令、删除、远程写操作以及有顺序依赖的调用必须串行，避免竞态和副作用顺序错误。即使标记为 safe，也要考虑同一文件锁、资源配额、取消传播和 MCP Server 是否支持并发；最稳妥的模型是显式声明读写集合和依赖图，而不是只靠一个布尔值。

### 指标与工程追问

#### 61. 安全决策准确率 100% 是准确率、召回率还是零误放率？如何避免只测简单样例？

当前指标名是 `decision_accuracy`，定义为预测 allow/deny 与期望标签相等的比例；它不是召回率，也不是零误放率。安全场景必须单独报告危险样本召回率和误放数，核心目标通常是高风险操作零误放，再同时监控正常操作误拒率。避免简单样例的方法是独立攻击集、命令变形/组合、跨平台路径、脚本和属性测试，且测试集不能与黑名单实现逐字同源；最好由人工设计、历史事件和模糊生成样本共同构成。

#### 62. 50 次连续工具调用为什么能全部完成？是否设置了最大步数或人工干预？

这里的 50 次是 benchmark 重复运行同一个确定性的两轮 FakeProvider 任务，不是一个任务真的连续调用 50 步。FakeProvider 第一轮调用 `bench_echo`，第二轮返回文本，因此 50/50 结束原因为 `finished`。AgentLoop 当前有默认 25 轮最大步数，也支持取消；权限确认由上层模式决定。这个结果只能说明固定编排场景稳定，不能证明真实模型在 50 步复杂任务上必然完成。

#### 63. 如果模型无法完成任务，系统怎样向用户解释失败原因并保留恢复入口？

系统应返回明确的结束原因：达到步数上限、用户取消、连续工具错误、权限拒绝、超时或流错误，并附上最后一次工具调用、错误摘要、已完成变更和测试状态。不要把“未完成”伪装成成功。会话 JSONL 保留现场，溢写文件保留完整输出，用户可修正参数、批准一次操作、恢复会话或继续执行；文件修改还应提供 diff/回滚入口。当前 Loop 已有 `LoopFinished.reason`，UI 和恢复命令应把这些原因展示得更完整。

#### 64. 这个终端 Agent 与 Claude Code、Cursor 类产品相比，核心差异是什么？

GXCode 的核心定位是轻量、可扩展的终端 Agent 核心：Provider 可插拔，工具通过 MCP 统一接入，AgentLoop、权限、上下文溢写、JSONL 会话和 Markdown 项目记忆都保持模块化，适合作为可审计的学习型或二次开发底座。

与 Claude Code 相比，GXCode 当前更强调协议和模块实现的透明性，但在成熟度、内置工具生态、代码库理解、沙箱和真实任务验证上仍需补强；与 Cursor 相比，GXCode 不以 IDE 编辑体验、索引、补全和图形化 diff 为核心，而是以终端自动化和可替换后端为核心。不能只用“功能更多”概括差异，真正应比较的是任务成功率、误操作率、恢复能力、权限边界、延迟、成本和生态兼容性。
