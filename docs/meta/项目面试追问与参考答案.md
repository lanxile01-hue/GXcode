# Mewagent 项目面试追问与参考答案

## 一、项目简介

Mewagent 是一个基于大语言模型的命令行 Agent 项目，核心目标是让模型能够理解用户任务，并根据任务自动选择和调用工具。项目支持 OpenAI 兼容接口和 Anthropic 接口，支持本地工具、stdio MCP Server 和 HTTP MCP Server 三种工具来源，同时具备流式输出、连续多轮工具调用、权限检查、上下文压缩、会话持久化和 Skill 扩展能力。

项目的核心闭环是：用户输入任务后，系统把对话历史、系统提示词和工具定义发送给模型；模型根据工具名称、描述和参数 Schema 判断是否需要调用工具；AgentLoop 执行模型返回的工具调用；工具结果再写回会话上下文；模型读取工具结果后继续决定下一步，直到不再调用工具并生成最终答案。

## 二、面试官：请你先介绍一下这个项目

### 参考回答

这个项目是一个基于大语言模型的命令行 Agent。它不是简单地把用户问题转发给模型，而是给模型提供一组结构化工具，让模型能够根据任务自主选择工具并完成多步操作。项目启动时会加载模型配置和 MCP 配置，连接外部 MCP Server，发现远程工具，并把这些工具统一注册到 ToolRegistry 中。用户输入任务后，AgentLoop 负责组织模型调用和工具执行：模型先分析任务，如果需要外部能力就返回 Tool Call，系统根据工具名称找到对应工具并执行，再把执行结果反馈给模型，模型继续处理下一步。这个过程可以连续执行多轮，直到模型认为信息已经足够并生成最终答案。项目同时加入了 Provider 抽象、stdio 和 HTTP 传输适配、权限检查、上下文压缩、会话 JSONL 持久化、Skill 工具和错误处理等能力。

## 三、面试官：整个项目的流程是怎样的？

### 参考回答

程序从 `src/gxcode/main.py` 的 `main()` 进入，先读取模型配置，并根据当前配置创建 OpenAI 或 Anthropic Provider。随后系统读取用户级和项目级 MCP 配置，通过 `MCPManager` 连接所有配置的 MCP Server。连接时，stdio Server 会启动一个子进程，通过 stdin 和 stdout 传递 JSON-RPC 消息；HTTP Server 则通过 HTTP POST 发送 JSON-RPC 请求。连接成功后，McpClient 依次完成 `initialize`、`notifications/initialized` 和 `tools/list`，获得每个 MCP Server 提供的工具定义。MCPManager 再使用 MCPToolWrapper 将远程工具适配为项目内部统一的 Tool 接口，并注册到 ToolRegistry。ToolRegistry 将工具转换成模型 API 所需的 Schema，随后 Provider 创建时把这些工具定义传给模型。命令行界面收到用户输入后创建 AgentLoop，AgentLoop 将系统提示词和用户消息加入 ChatSession，然后请求模型。如果模型只返回普通文本，说明本轮任务已经完成；如果模型返回 Tool Call，AgentLoop 就根据工具名从 ToolRegistry 中查找工具，先执行权限检查，再调用工具。工具返回结果后，结果会加入会话历史，AgentLoop 继续下一轮模型调用。这样就形成“模型决策—工具执行—结果反馈—继续决策”的循环。循环会在模型不再调用工具、用户取消任务、达到最大迭代次数或连续发生工具错误时结束。

核心调用链可以概括为：

```text
main.py
  → load_mcp_config()
  → MCPManager.connect_all()
  → McpClient.initialize()
  → McpClient.list_tools()
  → MCPToolWrapper
  → ToolRegistry.register()
  → ToolRegistry.to_api_schema()
  → Provider.stream_chat()
  → AgentLoop.run()
  → ToolRegistry.get()
  → Tool.execute()
  → ChatSession.add_tool_result()
  → 再次请求模型
```

## 四、面试官：项目的核心模块有哪些？

### 参考回答

项目主要分为以下几个模块：`main.py` 是启动入口，负责加载配置和组装各个组件；`provider` 模块负责对接不同模型供应商并解析流式响应；`agent` 模块中的 AgentLoop 负责模型调用和工具执行的循环编排；`tools` 模块定义统一的 Tool 接口、ToolResult 和 ToolRegistry；`mcp` 模块负责 MCP Server 的配置、传输、协议请求、工具发现和工具适配；`session.py` 负责保存当前会话历史；`context` 模块负责 Token 统计和上下文压缩；`permission` 模块负责工具调用前的权限检查；`skills` 模块负责加载和注册 Skill 相关工具；`tui` 模块负责将 Agent 的流式事件渲染到命令行界面。

主要文件如下：

| 文件 | 作用 |
|---|---|
| `src/gxcode/main.py` | 程序入口和依赖组装 |
| `src/gxcode/agent/loop.py` | Agent 主循环 |
| `src/gxcode/tools/registry.py` | 工具注册和 Schema 转换 |
| `src/gxcode/mcp/transport.py` | stdio/HTTP 传输层 |
| `src/gxcode/mcp/client.py` | MCP JSON-RPC 客户端 |
| `src/gxcode/mcp/manager.py` | MCP Server 连接和工具注册 |
| `src/gxcode/mcp/adapter.py` | 远程工具适配器 |
| `src/gxcode/provider/openai.py` | OpenAI 流式响应和 Tool Call 解析 |
| `src/gxcode/provider/anthropic.py` | Anthropic 流式响应和 Tool Use 解析 |
| `src/gxcode/session.py` | 对话历史和工具结果管理 |

## 五、Agent 编排与模型调用

### 1. 面试官：为什么需要 AgentLoop？直接调用模型不行吗？

### 参考回答

直接调用模型只能得到一次回复，而 Agent 任务通常需要多个步骤，例如先查询文件，再根据查询结果执行另一个工具，最后总结结果。AgentLoop 把一次任务拆成多个迭代，每一轮负责调用模型、收集模型输出、识别工具调用、执行工具和保存工具结果。这样模型可以基于上一轮工具结果继续决策，支持连续多轮操作。AgentLoop 还统一处理最大迭代次数、取消、权限检查、未知工具和连续错误等异常情况。

### 2. 面试官：AgentLoop 的停止条件有哪些？

### 参考回答

主要有四类停止条件。第一，模型没有返回工具调用，说明模型可以直接生成最终答案；第二，用户主动取消任务；第三，达到 `max_iterations`，避免模型陷入无限循环；第四，连续多轮只返回未知工具或工具错误，达到错误阈值后停止。对应代码主要在 `src/gxcode/agent/loop.py` 的 `run()` 方法中。

### 3. 面试官：模型是怎么知道应该使用哪个工具的？

### 参考回答

模型通过工具定义来判断，而不是依赖项目中的固定关键词路由。系统会把每个工具的名称、描述和 JSON Schema 参数传给模型。例如工具定义中包含 `get_time`、描述“获取当前时间”、以及参数结构，模型看到用户问“现在几点”时，就可能返回 `get_time` 的 Tool Call。模型选择工具的质量高度依赖工具描述和参数定义是否准确。代码中 `ToolRegistry.to_api_schema()` 负责生成工具 Schema，OpenAI Provider 和 Anthropic Provider 负责把 Schema 传给各自的模型接口。

### 4. 面试官：项目有没有自己实现工具选择算法？

### 参考回答

当前项目没有实现基于关键词的本地工具路由，主要依赖模型根据工具描述自主选择。程序侧只负责把工具定义传给模型、解析模型返回的工具名和参数、根据工具名查找并执行工具。这样可以减少硬编码，但也意味着工具描述质量、模型能力和工具数量会影响选择准确率。对于生产场景，可以进一步增加工具分组、工具白名单、规则预筛选或二阶段工具路由。

### 5. 面试官：模型返回工具调用后，代码是怎么处理的？

### 参考回答

OpenAI Provider 会从流式响应的 `delta.tool_calls` 中增量收集工具 ID、工具名称和参数字符串，等流结束后再解析 JSON 参数，生成统一的 `ToolCall` 对象。Anthropic Provider 则解析 `content_block_start`、`input_json_delta` 和 `content_block_stop` 等事件，最终也生成统一的 `ToolCall`。AgentLoop 不需要关心底层模型厂商的事件格式，只处理统一的 `ToolCall`，再通过 ToolRegistry 查找工具并执行。

## 六、工具系统与 MCP

### 6. 面试官：ToolRegistry 做了什么？

### 参考回答

ToolRegistry 是项目中的工具注册中心，内部通过工具名称保存 Tool 实例，提供 `register()`、`get()`、`list_all()` 和 `to_api_schema()` 方法。`register()` 用于注册本地工具或 MCP 适配工具，`get()` 根据模型返回的名称查找工具，`list_all()` 用于生成系统提示词中的工具列表，`to_api_schema()` 用于生成 OpenAI 和 Anthropic 都能使用的工具定义。这样模型看到的是统一格式，AgentLoop 执行的也是统一的 `tool.execute(**kwargs)` 接口。

### 7. 面试官：为什么需要 MCPToolWrapper？

### 参考回答

MCP Server 的工具调用方式是 MCP JSON-RPC 的 `tools/call`，而项目内部工具统一要求实现 `execute()` 方法。如果让 AgentLoop 直接处理 MCP 协议，就会把 Agent 编排逻辑和远程协议耦合在一起。MCPToolWrapper 将 MCP 工具定义映射成内部 Tool 的 `name`、`description`、`parameters` 和 `execute()`，AgentLoop 只需要调用统一接口，具体是否通过 MCP、stdio 或 HTTP 完成则由适配器和客户端负责。

### 8. 面试官：MCP 的完整调用流程是什么？

### 参考回答

首先由 MCPManager 根据配置创建 StdioTransport 或 HttpTransport，然后创建 McpClient 并调用 `connect()`。接着客户端发送 `initialize` 请求，完成协议版本、能力和客户端信息协商，再发送 `notifications/initialized` 通知。之后调用 `tools/list` 获取工具定义并注册到 ToolRegistry。当模型选择某个 MCP 工具时，MCPToolWrapper 的 `execute()` 调用 McpClient 的 `call_tool()`，客户端发送 `tools/call` 请求，传输层负责实际发送并读取响应，最后适配器将 MCP 返回的 content 文本转换为 ToolResult。

### 9. 面试官：stdio 和 HTTP 的区别是什么？

### 参考回答

stdio 适合本机启动的工具服务，优点是部署简单、进程隔离，不需要额外暴露网络端口；缺点是工具服务生命周期和客户端进程绑定，远程复用能力较弱。HTTP 适合独立部署和跨进程、跨机器访问，便于多个客户端复用；缺点是需要处理网络超时、鉴权、连接失败和服务发现等问题。项目通过统一的 `JsonRpcTransport` 抽象隐藏了两者差异，McpClient 只依赖 `send()`、`receive()` 和 `close()`。

### 10. 面试官：当前 HTTP MCP 实现是不是完整的流式 HTTP？

### 参考回答

当前代码实现的是基于 HTTP POST 的 JSON-RPC 请求—响应模式，`HttpTransport` 发送请求后读取完整 JSON 响应。代码注释使用了 Streamable HTTP 的表述，但当前实现没有完整处理 SSE、多事件响应或异步通知流。如果面试官追问生产化改造，我会说明需要补充响应媒体类型判断、SSE 事件解析、请求 ID 与响应匹配、通知处理、重连和超时机制。

### 11. 面试官：MCP Server 连接失败时系统怎么办？

### 参考回答

`MCPManager.connect_all()` 对每个 Server 单独捕获异常并记录日志，某个 Server 连接失败时会跳过它，继续连接其他 Server，并返回已经成功注册的工具。因此单个外部服务故障不会直接阻塞整个 Agent 启动。不过当前实现更偏向启动时容错；如果生产环境需要动态恢复，还应增加重连、健康检查和工具不可用状态管理。

## 七、连续多轮工具操作

### 12. 面试官：请具体讲一下连续多轮工具调用是怎么实现的？

### 参考回答

AgentLoop 的 `run()` 方法内部有一个循环。第一轮先把用户消息放入 ChatSession，然后调用 Provider 获取模型响应。如果模型返回工具调用，就执行这些工具并把结果通过 `add_tool_result()` 写回会话历史。之后循环继续，下一轮模型请求会携带之前的用户消息、模型回复和工具结果，模型可以基于这些信息选择另一个工具或直接回答。只要模型持续返回 Tool Call，循环就持续执行；当模型返回普通文本时，系统将文本作为最终答案并退出。这个机制本质上是一个受最大迭代次数约束的 ReAct 循环。

### 13. 面试官：举一个连续多轮操作的例子。

### 参考回答

例如用户提出“先获取当前时间，再把时间回显出来”。第一轮模型根据工具描述选择 `get_time`，系统执行后得到时间结果；第二轮模型读取工具结果，选择 `echo`，并把时间作为参数传入；第三轮模型看到两个工具都已经完成，不再返回 Tool Call，而是生成“当前时间已经获取并回显”的最终回复。这里每一轮的关键是工具结果必须写回上下文，否则模型无法知道上一轮发生了什么。

### 14. 面试官：多个工具调用是并行还是串行？为什么？

### 参考回答

当前 AgentLoop 会根据工具的 `is_safe` 属性进行区分。安全工具可以使用 `asyncio.gather()` 并发执行，适合多个互不依赖的只读查询；非安全工具会串行执行，适合有副作用的写操作或需要控制顺序的操作。这样可以在保证安全性的同时降低只读任务的延迟。更完善的生产实现还需要显式表达工具依赖关系，不能只依赖安全属性判断是否可以并发。

### 15. 面试官：工具结果为什么要写回会话？

### 参考回答

因为工具执行本身不会改变模型的上下文。模型下一轮请求时只能看到 ChatSession 中的历史消息，如果不把工具结果写回，模型就不知道工具是否成功、返回了什么数据，也无法据此决定下一步。当前项目通过 `ChatSession.add_tool_result()` 将工具名称和结果加入历史，下一轮 Provider 会携带完整历史继续请求模型。

## 八、会话、上下文与 Skill

### 16. 面试官：ChatSession 负责什么？

### 参考回答

ChatSession 负责维护当前会话的 Provider、模型、系统提示词、消息历史和可选的 SessionStore。它提供添加 system、user、assistant 和 tool result 消息的方法。接入 SessionStore 后，用户消息、模型回复和工具结果还会以 JSONL 形式持久化。AgentLoop 负责流程控制，ChatSession 负责上下文和历史管理，两者职责是分开的。

### 17. 面试官：为什么需要上下文压缩？

### 参考回答

连续多轮工具任务会不断增加消息历史，最终可能超过模型上下文窗口，导致请求失败、成本增加或模型注意力下降。项目在每轮模型调用前通过 ContextManager 检查 Token 使用情况，达到阈值时进行压缩。压缩的目标是保留最近对话和关键事实，同时把较早内容总结成更短的上下文。上下文压缩属于可靠性能力，而不是单纯的性能优化。

### 18. 面试官：压缩之后如何避免丢失订单号等关键信息？

### 参考回答

压缩不能简单删除旧消息，而应该保留最近若干轮，并将早期消息摘要化。对于订单号、用户偏好、当前任务状态等关键事实，应通过记忆模块或结构化字段单独保存，再在后续请求时注入系统上下文。当前项目已有 ContextManager、SessionStore 和 Memory 相关模块，生产环境还可以增加关键事实抽取和压缩后的回归校验。

### 19. 面试官：Skill 模块解决什么问题？

### 参考回答

Skill 用于把一组可复用的任务说明、工具依赖和使用规则组织起来。启动时 SkillLoader 加载项目中的 Skill，ToolWhitelist 校验 Skill 声明的工具是否已经注册，SkillRegistry 管理 Skill 内容和摘要，并通过 `load_skill` 等工具让 Agent 按需加载。这样可以把复杂能力从一个巨大 System Prompt 中拆出来，减少初始上下文，并支持按任务动态激活。

## 九、模型 Provider 设计

### 20. 面试官：为什么要抽象 Provider？

### 参考回答

OpenAI 和 Anthropic 的请求格式、认证头、流式事件和工具调用事件并不完全相同。如果 AgentLoop 直接调用某一家模型接口，后续切换模型就需要修改核心编排逻辑。项目定义了统一的 Provider 接口，AgentLoop 只调用 `stream_chat()` 并接收统一的 StreamEvent、TextDelta、ToolCall、ErrorEvent 等对象，具体协议差异由 OpenAIProvider 和 AnthropicProvider 内部处理。

### 21. 面试官：流式输出是怎么实现的？

### 参考回答

Provider 使用异步 HTTP 客户端建立流式连接，逐行读取模型返回的 SSE 数据，并把文本增量转换成 TextDelta 事件。工具调用参数可能也是分片返回的，所以 Provider 会先按工具索引或当前工具块累积参数字符串，等参数完整后再解析成 JSON 并生成 ToolCall。上层 UI 通过消费这些事件，可以实时显示模型文本、思考内容、工具调用和执行结果。

### 22. 面试官：工具定义同时传给 OpenAI 和 Anthropic，格式一样吗？

### 参考回答

项目的 ToolRegistry 输出的是统一的 function tool Schema，Provider 层负责将其放到各自 API 的请求体中。当前 OpenAI Provider 使用 `tools` 字段，Anthropic Provider 也将工具定义放入 `tools` 字段，但两者返回事件格式不同，因此重点是输入工具 Schema 做统一、输出事件在 Provider 内部做适配。

## 十、权限、安全和错误处理

### 23. 面试官：工具调用前为什么要做权限检查？

### 参考回答

模型返回工具调用不代表这个操作一定被允许。尤其是删除文件、执行命令或远程写操作，不能只相信模型判断。AgentLoop 在 `_execute_tool()` 中调用 PermissionChecker 检查工具名称和参数，拒绝的调用会转换为失败的 ToolResult 并反馈给模型。对于生产系统，还需要在工具服务端做二次鉴权，因为客户端侧检查不能替代真正的业务权限控制。

### 24. 面试官：如何防止模型调用不存在的工具？

### 参考回答

工具 Schema 只向模型暴露已注册工具，AgentLoop 执行前还会通过 ToolRegistry 再查一次。如果模型返回未注册工具，系统会生成明确的错误结果，而不是直接崩溃。连续多轮都只返回未知工具时，达到错误阈值后结束任务，避免无限错误循环。

### 25. 面试官：工具执行失败后怎么办？

### 参考回答

工具执行过程被统一捕获，成功时返回 `ToolResult.ok()`，异常时返回 `ToolResult.fail()`。AgentLoop 会把失败原因写回上下文，让模型知道工具没有成功。对于临时网络错误，生产环境可以在工具适配层增加有限次数重试和指数退避；对于权限拒绝、参数错误和业务状态不允许等确定性错误，则应该直接向用户解释原因或请求补充信息，不能盲目重试。

### 26. 面试官：如何避免 Agent 无限调用工具？

### 参考回答

项目通过最大迭代次数、取消事件和连续错误计数控制循环。最大迭代次数限制正常情况下的循环长度，取消事件支持用户主动停止任务，连续错误计数用于处理模型反复调用未知工具的情况。生产环境还可以增加单次任务总 Token、总耗时、单工具调用次数和高风险操作次数限制。

## 十一、配置与运行

### 27. 面试官：MCP 配置从哪里读取？

### 参考回答

配置加载代码在 `src/gxcode/mcp/config.py`。系统会先读取用户级的 `~/.gxcode/mcp_servers.yaml`，再读取项目级 `.gxcode/mcp_servers.yaml`，项目级配置可以覆盖用户级同名配置。配置中的 `${VAR}` 会被替换成环境变量，适合保存 URL、Token 和其他部署相关参数。当前项目的示例配置位于 `.gxcode/mcp_servers.yaml`。

### 28. 面试官：项目如何切换不同模型？

### 参考回答

模型协议和模型参数通过配置文件读取，`create_provider()` 根据 `protocol` 选择 OpenAIProvider 或 AnthropicProvider。这样可以在不改 AgentLoop 的情况下切换不同供应商或兼容接口。需要注意，项目代码只能说明支持某种协议或模型配置，不能把“代码支持切换”表述成“已经在生产环境使用了某个具体模型”，实际模型应以运行配置和日志为准。

## 十二、测试与项目真实性追问

### 29. 面试官：你如何证明这个项目真的支持 MCP？

### 参考回答

项目中有完整的 MCP 客户端链路，包括 `transport.py` 的 stdio/HTTP 传输、`client.py` 的 `initialize`、`list_tools` 和 `call_tool`、`manager.py` 的 Server 管理和工具注册，以及 `adapter.py` 的 Tool 包装。同时项目目录中的 `test_mcp_server.py` 提供了一个最小 MCP Server，能够通过 `tools/list` 暴露 `echo` 和 `get_time` 工具，通过 `tools/call` 返回结果。测试时可以启动项目并让模型调用这些工具，或者使用 Fake Client 做适配器单元测试。

### 30. 面试官：你如何测试连续工具调用？

### 参考回答

可以使用固定的 Mock Provider，让第一轮返回 `get_time` Tool Call，工具返回固定时间；第二轮根据工具结果返回 `echo` Tool Call；第三轮返回普通文本。然后验证工具调用顺序、参数是否正确、工具结果是否写入会话，以及 AgentLoop 是否在最终文本出现后停止。这样可以稳定测试 ReAct 循环，而不依赖真实模型的随机性。

### 31. 面试官：为什么不能只测试最终答案？

### 参考回答

只看最终答案可能掩盖工具调用错误，例如模型调用了错误工具、参数不正确、调用顺序不合理，最后却生成了看起来正确的文本。Agent 项目需要同时检查最终结果和中间轨迹，包括工具名称、工具参数、调用次数、返回结果、错误处理和停止原因。当前项目的事件模型包含 ToolCall、ToolResultEvent、IterationStart、IterationEnd 和 LoopFinished，适合做过程观测。

### 32. 面试官：这个项目当前有哪些可以继续改进的地方？

### 参考回答

第一，可以为不同工具增加更细粒度的权限、参数校验和服务端鉴权；第二，可以完善 HTTP MCP 的 SSE、多响应和通知处理；第三，可以在 ToolRegistry 前增加工具分组或二阶段筛选，减少大量工具同时暴露给模型造成的选择压力；第四，可以增加 Trace，记录每轮模型请求、工具调用、Token、延迟和错误；第五，可以为 AgentLoop 增加工具调用重试、超时和降级策略；第六，可以使用更标准的 assistant tool call 和 tool result 消息结构，提升不同模型 API 的兼容性；第七，可以补充固定的 Mock Provider 和 MCP 集成测试，验证连续多轮调用和异常场景。

## 十三、项目流程的一段式面试回答

### 参考回答

这个项目是一个基于大语言模型的命令行 Agent，核心目标是让模型根据用户任务自动选择工具并完成连续多轮操作。程序从 `main.py` 启动，先加载模型配置和 MCP 配置，然后由 `MCPManager` 根据配置连接外部 MCP Server。项目支持 stdio 和 HTTP 两种接入方式，stdio 通过启动外部子进程并使用标准输入输出传递 JSON-RPC 消息，HTTP 则通过 HTTP POST 与远程 Server 通信。连接成功后，McpClient 依次执行 `initialize`、初始化通知和 `tools/list`，获得外部工具的名称、描述和参数 Schema，再由 MCPToolWrapper 将远程工具适配成项目内部统一的 Tool 接口，并注册到 ToolRegistry。ToolRegistry 将本地工具和 MCP 工具统一转换成模型可理解的 function tool 定义，并传给 OpenAI 或 Anthropic Provider。用户输入任务后，界面层启动 AgentLoop，AgentLoop 将系统提示词和用户消息加入 ChatSession，然后调用模型。模型会根据用户任务和工具定义判断是否需要调用工具，如果不需要就直接生成最终答案，如果需要就返回 Tool Call。Provider 负责解析不同模型的流式响应，并统一转换成内部 ToolCall 对象。AgentLoop 收到 Tool Call 后，根据工具名称从 ToolRegistry 查找工具，先做权限检查，再执行工具；如果是 MCP 工具，就通过 MCPToolWrapper 调用 McpClient，最终由 stdio 或 HTTP 传输层完成远程请求。工具执行结果会被包装成 ToolResult 并写回 ChatSession，AgentLoop 再次请求模型，模型根据工具结果继续调用其他工具或生成最终回复。因此整个系统形成了“模型决策、工具执行、结果反馈、继续决策”的 ReAct 闭环。项目还通过最大迭代次数防止无限循环，通过错误计数处理连续工具错误，通过安全属性区分工具的并发和串行执行，通过 ContextManager 进行上下文压缩，通过 SessionStore 保存会话，通过 SkillLoader 和 ToolWhitelist 扩展和约束技能。这个项目最核心的设计是把不同来源的工具统一抽象成 Tool 接口，让 AgentLoop 不需要关心工具来自本地、stdio 还是 HTTP，只负责完成模型和工具之间的编排。

## 十四、面试回答时的注意事项

### 1. 不要把当前项目没有实现的能力说成已经实现

当前项目重点是单 Agent ReAct、MCP 工具接入、Provider 抽象、上下文管理、Skill 和权限控制。不要直接套用其他项目中的 Multi-Agent、LangGraph、Adaptive-RAG、BM25、Cohere 重排、Guardrails Judge 等表述，除非代码中确实存在对应实现。

### 2. 正确区分“支持”和“已经使用”

可以说“代码支持 OpenAI 和 Anthropic 两种 Provider”，但不能在没有运行配置或日志证据时说“项目已经在线使用某个具体模型”。同样，可以说“项目支持 HTTP MCP 接入”，但当前实现主要是 HTTP 请求—响应模式，不应夸大成完整的 SSE 流式实现。

### 3. 最重要的项目亮点

面试时建议突出以下三点：

1. 通过 Tool 接口和 MCPToolWrapper 统一本地工具与远程工具。
2. 通过 AgentLoop 实现模型自主选择工具和连续多轮 ReAct 闭环。
3. 通过 Provider、Transport、Registry、Session 等抽象降低模块耦合，方便替换模型、工具来源和存储方式。

### 4. 最后总结

这个项目的核心不是简单地调用一次大模型，而是构建了一个可扩展的 Agent 执行框架：模型负责理解任务和提出工具调用，系统负责工具发现、权限控制、参数传递和结果反馈，AgentLoop 负责把这些步骤组织成可持续、可终止、可观测的多轮执行过程。
